# Poker vision agent: where screen-reading breaks

A computer-use style agent plays heads-up no-limit hold'em **only through screenshots**.
It never sees the game state. Every decision goes: render the table to an image → add
screen noise → read the image with a vision pipeline → run a fixed policy on what it read
→ click. The same policy also plays the same seeded hands on the **true** state, so every
gap is caused by perception alone.

Scope and rules: local open-source simulator (PokerKit) against simple bots, plus Slumbot's
public bot-vs-bot API (no money). No real poker sites, no real people, no money, no paid
APIs, no evasion or human-mimicry. Everything here is free and runs on a CPU.

## Rerun

```bash
./run_all.sh              # local study: ~40 min on 8 cores (WORKERS=4 by default; incl. the review anchor experiment)
./run_all.sh --slumbot    # + phase 2 against slumbot.com (~2 h, polite 0.5 s pauses)
```

Outputs land in `results/` (CSV/JSON) and `charts/` (PNG). Two large raw outputs are **not
committed** and are regenerated by `./run_all.sh`: `results/decisions.csv.gz` (per-decision log,
~10 MB) and `results/perception_bench.csv` (per-frame bench, ~6 MB). Everything derived from them
(summary tables, `summary.json`, `review_checks.json`, charts) is committed. Seeds are fixed
(`PYTHONHASHSEED=0`, stable CRC32 seeds), so a rerun reproduces the local numbers exactly.
The Slumbot numbers will differ (live opponent, new cards).

Optional, separate venv because torch is heavy:
```bash
python3 -m venv .venv-vlm && .venv-vlm/bin/pip install -r requirements.txt torch transformers --extra-index-url https://download.pytorch.org/whl/cpu
cd src && ../.venv-vlm/bin/python vlm_probe.py 50 clean,realistic_mix ../results/vlm_probe_smolvlm256m.csv
```

## What is in here

| File | What it does |
|---|---|
| `src/table.py` | Renders a 960×600 table (3 themes: classic, four-colour deck, dark). |
| `src/noise.py` | 8 screen conditions: clean, JPEG q20, 0.5× scale, Gaussian blur 1.5, animated chips over the felt, four-colour theme, dark theme, and `realistic_mix` (0–2 chip stacks + 0.75× scale + blur 0.6 + JPEG 55). |
| `src/vision.py` | Classic CV reader. Template matching for ranks/suits, connected-component OCR for numbers, colour tests for card/plate/button presence. `naive` (grayscale) and `hardened` (polarity normalisation + Otsu + glyph-height filtering) modes. |
| `src/policy.py` | Fixed policy: Monte Carlo equity vs a random hand (300 samples, seeded) + pot odds + sizing rules. Not a strong player on purpose; the study measures the gap, not the win rate. |
| `src/game.py` | PokerKit hand loop vs two bots (`tag`, `station`), duplicate-seeded: deck, stacks, button, opponent and a ±4 px window offset are fixed per hand. |
| `src/agent.py` | Ground-truth agent and vision agent. Optional guardrails: duplicate card, board count, board shrank, hole cards changed, low match confidence, chips not conserved within the hand; up to 3 frames, then fall back to check/fold. |
| `src/perception_bench.py` | 2,000 real game states × 8 conditions × 2 readers, scored field by field. |
| `src/run_matches.py` | Ground truth + 16 vision configs, 3,000 duplicate hands each (51,000 hands). |
| `src/slumbot_client.py` | Phase 2 client for slumbot.com's public API (gt or vision mode, resumable, 0.5 s pauses). |
| `src/slumbot_field_check.py` | Offline re-read of every Slumbot state's chip numbers to see which fields fail at 200bb depth. |
| `src/vlm_probe.py` | Small local open VLM (SmolVLM-256M-Instruct, CPU) on the same screenshots. |
| `src/analyze.py` | All tables, `results/summary.json`, the cost estimate and the charts. |
| `src/review_checks.py` | Independent review checks on existing results (guardrail anchoring, loss tails, Slumbot diff). Writes `results/review_checks.json`. |
| `src/review_anchor_fix.py` | Review experiment: guarded agent whose chip-conservation anchor must be confirmed by two agreeing frames. Not part of the headline tables. |

## Results (from the files in `results/`)

### Perception, 2,000 states per condition (`perception_accuracy.csv`)

Share of screenshots where **every** field (2 hole cards, board, pot, 2 stacks, 2 bets, button) was read correctly:

| Condition | naive | hardened |
|---|---|---|
| clean | 100.0% | 98.8% |
| jpeg_q20 | 100.0% | 99.0% |
| theme_four_color | 100.0% | 98.8% |
| theme_dark | 0.0% | 98.8% |
| chip_overlap | 72.8% | 75.4% |
| scale_0.5 | 54.5% | 87.2% |
| blur_1.5 | 0.0% | 10.1% |
| realistic_mix | 65.1% | 74.5% |

- Cards are the easy part: ≥98.6% per card everywhere except naive + dark theme (1.2%: light ink on dark faces, 81% of misread cards come out as a "10").
- Numbers are the hard part. Blur 1.5 breaks every number for the naive reader (`200` → `24143`, `12,920` → `124243`): blurred commas and touching digits become extra glyphs.
- The hardened reader fixed the dark theme but **introduced a new bug**: it reads some `2`s as `7` and `6`s as `0` on bet plates (`120` → `170`, `200` → `700`), 1.2% of clean frames. The chip-conservation guardrail caught all of them in play.
- Perception latency: 6–13 ms mean per frame, p95 ≤ 18 ms, single thread.

### Decisions, 3,000 duplicate hands per config (`match_summary.csv`, `match_by_opponent.csv`, `guardrail_diagnostics.csv`)

Ground truth policy: −79.7 ± 66.2 bb/100 overall (−214.7 vs `tag`, +59.4 vs `station`).

| Config | decisions on a wrong state | actions different from ground truth | gap vs GT, all hands (bb/100, 95% CI) | gap vs station only |
|---|---|---|---|---|
| naive, realistic_mix | 35.3% | 5.8% | −73.5 ± 49.2 | −112.3 ± 66.8 |
| naive, chip_overlap | 27.0% | 6.2% | −243.3 ± 74.4 | −337.2 ± 114.6 |
| naive, theme_dark | 100% | 37.3% | −123.1 ± 62.1 | −193.4 ± 55.4 |
| naive, blur_1.5 | 100% | 10.3% | −946.9 ± 126.1 | −1424.3 ± 204.9 |
| naive, scale_0.5 | 46.2% | 1.2% | +23.0 ± 22.9 | +6.8 ± 9.4 |
| guarded, realistic_mix | 9.2% (acted) + 30.5% fallback | 23.0% | +70.0 ± 60.0 | −51.2 ± 57.7 |
| guarded, blur_1.5 | 8.6% (acted) + 87.7% fallback | 47.0% | +41.9 ± 65.8 | −90.4 ± 63.1 |

How to read the money column: the policy loses to the `tag` bot, so folding more (which is what a check/fold fallback does) **looks** like a gain overall. Against `station`, where the policy wins, the guarded agent still pays for every fallback. The honest per-config cost is the station column plus the mismatch rate.

Other findings:
- A wrong state rarely changes the action: on realistic_mix 35% of naive reads were wrong somewhere, but only 16.5% of those changed the click. Most errors land on a field the policy barely uses at that moment.
- The losses come from a few hands: on naive realistic_mix misreads changed the result of 518 of 3,000 hands; the worst 1% (30 hands) account for 144% of the net loss, and the best 30 won back 79% of it (`review_checks.json`).
- Most common naive realistic_mix flip: big blind `100` read as `106` preflop, which moves the price just enough to flip check ↔ call and call ↔ fold.
- Guardrails are blunt. On realistic_mix 66.8% of fallbacks happened when the last frame was actually right. **Review finding:** 1,307 of those 1,819 come from the chip-conservation check anchored on a misread: the check compares each read with the total from the last *acted* read, and the first acted read of a hand is never checked, so when it is wrong (29.3% of hands with an acted decision on realistic_mix) every later correct frame fails. 81% of the 9.2% acted-on-wrong-state decisions are exactly those unchecked first reads. The rest of the wasted fallbacks are low-confidence flags on correct reads. A variant that only accepts the anchor when two frames agree (`src/review_anchor_fix.py`, `results/review_anchor_fix/summary_realistic_mix.json`, 3,000 hands, same seeds) did not help: fallback 32.3% vs 30.5%, acted on a wrong state 8.0% vs 9.2%, gap vs station −53.2 ± 57.7 vs −51.2 ± 57.7 bb/100. Fallbacks moved to the first decision of the hand (34.9% vs 24.2%). Not in the tables above.
- Decision latency (render + noise + read + policy): naive realistic_mix p50 24.9 ms / p95 31.8 ms; guarded realistic_mix p50 28.8 / p95 87.1 ms (up to 3 frames). Equity calc with a cold cache is ≈5.8 ms.

### Phase 2: Slumbot (`results/slumbot/`, `slumbot_summary.json`)

Slumbot's public API (slumbot.com, heads-up NLHE, 50/100 blinds, 200bb stacks reset every hand, no money).
One request at a time per stream, 0.5 s pause before every request, research User-Agent. Two streams
ran 2026-10-26 ~12:27–13:21 (UTC+1) and were stopped at 534 completed hands each (1,068 total,
under the 2,000 cap); the client is resumable to 1,000 each.

| Run | hands | decisions | bb/100 (95% CI) |
|---|---|---|---|
| ground-truth state from the API | 534 | 1,827 | +15.6 ± 181.3 |
| vision: API state rendered to a screenshot (realistic_mix), naive reader | 534 | 1,749 | −366.8 ± 244.5 |

- Difference −382 bb/100, ±304 (independent samples: different cards, no duplicate deals, no AIVAT). Suggestive, not conclusive.
- Vision decisions on a wrong state: 31.0%. Clicks different from what the ground-truth policy would do on the same state: 5.0%. Both close to the local realistic_mix numbers (35.3% / 5.8%).
- Counterfactual on the same frames: the hardened reader would have been worse here (31.8% wrong states, 13.7% different clicks). `slumbot_field_check.py` shows why: on Slumbot's numbers it reads the villain's bet right only 76.0% of the time vs 96.4% for naive (the 2→7 bug; bets of 200, the standard 2bb open, dominate Slumbot's action strings). Naive's weak spot here is the hero's bet (78.7%).
- Perception 20.7 ms mean per frame (both readers ran on every frame).

### Small local VLM (`vlm_probe_smolvlm256m.csv`)

SmolVLM-256M-Instruct (Apache-2.0, ~256M params), CPU, greedy decoding, same prompt for every frame
asking for the state as JSON. 50 states × {clean, realistic_mix}:

- Fully correct states: 0/50 on both. Correct hero cards: 0/50 on both. No numeric field was ever put under the right key.
- It's not blind: the hero's stack string shows up somewhere in its output on 28/50 (clean) and 33/50 (realistic_mix) frames. It just doesn't bind values to fields, and it never produced both hole cards.
- ~18 s per frame (median 17.7 s clean, 18.2 s realistic_mix) on 2 CPU threads, sharing the box with other runs. The CV reader takes ~7 ms.

This is the smallest open VLM I could run on this box; it says nothing about larger or hosted models.

### Hosted VLM cost: ESTIMATE, not a run (`cost_estimate.json`)

Nothing was sent to any paid API. If a hosted VLM read one screenshot per decision
instead of the CV pipeline: 3.77 decisions per hand (measured), 5.09 frames per hand for the guarded agent on realistic_mix (measured), 1,120 image tokens per
screenshot (Gemini 3/4 default and `high` media resolution, [docs](https://ai.google.dev/gemini-api/docs/media-resolution)),
~400 prompt tokens, ~150 output tokens, no thinking tokens. Prices from
[ai.google.dev/gemini-api/docs/pricing](https://ai.google.dev/gemini-api/docs/pricing), read 2026-10-26:

| Model (standard tier) | $/call | $ per 1,000 hands (1 frame per decision) | guarded agent (5.09 frames per hand) |
|---|---|---|---|
| gemini-3.8-flash, through 2026-12-31 ($0.75 in / $3.75 out per 1M) | $0.0017 | $6.41 | $8.62 |
| gemini-3.8-flash, from 2027-01-01 ($1.50 / $7.50) | $0.0034 | $12.82 | $17.24 |
| gemini-3.5-flash-lite ($0.30 / $2.50) | $0.0008 | $3.13 | $4.21 |

Thinking tokens would be billed at the output price and can dominate this.

## Limitations

- Synthetic renderer and noise. A real client has animations, overlays, popups and fonts I did not model. The layout is hand-calibrated; a new client means recalibration.
- The policy is weak (it loses heavily to the `tag` bot). bb/100 gaps depend on the policy; mismatch rates and per-field accuracy depend much less on it.
- bb/100 CIs are wide even at 3,000 duplicate hands. Slumbot results have no variance reduction (no AIVAT, no duplicate deals).
- Thresholds and guardrails were tuned by me on the same distribution I test on.
- The chip-conservation guardrail anchors on an unchecked first read (see above), which inflates fallbacks on realistic_mix and scale_0.5.
- No hosted VLM was run (no spend). The cost table is arithmetic on published prices.

## Context: public LLM poker benchmarks (not my runs)

- GTO Wizard Benchmark ([arXiv 2603.23660](https://arxiv.org/abs/2603.23660), March 2026): text state, 5,000 hands per model vs GTO Wizard AI, AIVAT. LLMs from −16 ± 3 (GPT-5.3 Extra High) down to −189.7 (GPT-5.4 Nano); Grok 4 High −60 ± 15.1; Always Fold −64.6 ± 3.3 bb/100. ± is the paper's standard deviation, not a 95% CI.
- Kaggle Game Arena, [Heads-Up Poker leaderboard](https://www.kaggle.com/benchmarks/kaggle/poker-heads-up) (text harness, updated 2026-10-08): top mean +30 BB/100 (GPT-5.6 Sol). Models play each other, so this is relative to the pool.
- BluffBench (bluffbench.com, v0.3 beta, last updated 2026-05-20): multi-player, chips per 100 hands, top +1,568 (GPT-5.5 xHigh).
